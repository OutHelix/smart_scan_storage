**Тема: ML-сервис интеллектуального хранения сканированных документов**

### **Выбор темы проекта**

В современных организациях значительная часть информации по-прежнему
хранится в виде бумажных документов, которые после сканирования
превращаются в неструктурированные данные. Основная проблема заключается
не в хранении таких документов, а в их эффективном использовании: поиск,
классификация и извлечение информации требуют значительных ручных
усилий.

Интеллектуальное хранилище сканированных документов решает эту задачу за
счёт применения методов машинного обучения. Оно позволяет автоматически
распознавать текст, определять тип документа и извлекать ключевые
данные. Это делает систему не просто архивом, а полноценным инструментом
работы с информацией. Проект интересен тем, что объединяет компьютерное
зрение, OCR и обработку естественного языка в рамках единого ML-сервиса.

### **Бизнес-задача и её ML-интерпретация**

Основная цель системы — сократить время обработки документов и снизить
долю ручного труда. Сотрудники получают возможность быстро находить
нужные документы и автоматически извлекать из них ключевые данные, такие
как суммы, даты и контрагенты. Это ускоряет бизнес-процессы и снижает
вероятность ошибок.

С точки зрения машинного обучения задача сводится к обработке
неструктурированных изображений документов. Система должна распознавать
текст (OCR), определять тип документа (классификация) и извлекать
значимую информацию (NER). Сложность заключается в разнообразии
форматов, качестве сканов и отсутствии строгой структуры данных.
ML-подход позволяет выявлять скрытые закономерности и адаптироваться к
новым типам документов без жестко заданных правил.

**Входные данные:** сканированные документы (PDF, JPG, PNG), изображения
различного качества (шум, перекосы, низкое разрешение), метаданные (дата
загрузки, источник, тип файла), опционально — размеченные данные для
обучения моделей.

**Выходные данные:** распознанный текст документа (OCR), тип документа
(счет, договор, акт и др.), извлечённые ключевые поля (дата, сумма,
контрагент и т.д.), структурированные данные для хранения и поиска,
опционально — оценки уверенности модели.

### **Метрики качества**

**Бизнес-метрики:**

- Снижение времени обработки документов — чем выше точность моделей
  OCR и извлечения данных, тем меньше требуется ручного труда и быстрее
  обрабатываются документы.

- Доля автоматически обработанных документов (%) — показывает, какая
  часть документов проходит полный цикл без участия человека; напрямую
  зависит от качества моделей.

- Снижение количества ошибок при вводе данных (%) — корректное
  извлечение полей (суммы, даты, реквизиты) уменьшает финансовые и
  юридические риски.

- Время поиска документов — качественная классификация и индексация
  позволяют быстрее находить нужную информацию в хранилище.

**ML-метрики:**

- Accuracy — используется для оценки точности классификации типов
  документов (например, счет, договор, акт).

- Precision — показывает долю корректно извлечённых сущностей среди
  всех извлечённых моделью.

- Recall — отражает полноту извлечения значимых данных из документа.

- F1-score — баланс между precision и recall, ключевая метрика для
  задач извлечения информации.

- CER (Character Error Rate) — оценивает долю ошибок на уровне
  символов при распознавании текста.

- WER (Word Error Rate) — показывает ошибки на уровне слов, важна для
  читаемости текста.

| Бизнес-метрика | Как рассчитывается | Как качество модели влияет на бизнес |
|----------------|-------------------|--------------------------------------|
| Снижение времени обработки документов | Сравнение среднего времени обработки документа вручную и с использованием системы | Чем точнее OCR и извлечение данных, тем меньше требуется ручной работы и быстрее обрабатываются документы. Низкое качество моделей увеличивает время на проверку и исправление ошибок. |
| Доля автоматически обработанных документов (%) | Процент документов, прошедших обработку без участия человека | Высокое качество моделей увеличивает уровень автоматизации и снижает нагрузку на сотрудников. Низкая точность требует частого вмешательства человека. |
| Снижение количества ошибок при вводе данных (%) | Сравнение числа ошибок до и после внедрения системы | Точные модели уменьшают вероятность критических ошибок (в суммах, датах, реквизитах). Ошибки моделей могут приводить к финансовым и юридическим рискам. |
| Время поиска документа | Среднее время нахождения нужного документа в системе | Хорошая классификация и индексация ускоряют поиск и доступ к информации. Ошибки в классификации затрудняют поиск и снижают эффективность работы. |

В качестве источника данных используются наборы сканированных документов
из открытых датасетов, таких как RVL-CDIP (Ryerson Vision Lab Complex
Document Information Processing) и FUNSD (Form Understanding in Noisy
Scanned Documents).

Обоснование выбора: данные содержат реальные сканированные документы
различных типов (счета, формы, письма), включают разметку для задач
классификации и извлечения информации, а также отражают разнообразие
форматов и качества изображений. Это позволяет обучать модели,
устойчивые к шуму, перекосам и различным структурам документов.

Характеристики датасета: изображения документов в форматах PDF и PNG,
наличие текстовых аннотаций и разметки сущностей, большое количество
классов документов, разнообразие структур (таблицы, формы, свободный
текст), а также вариативность качества сканов (шум, искажения, низкое
разрешение).

### **Высокоуровневая архитектура системы**

Контекстная диаграмма потоков данных верхнего уровня для сервиса
интеллектуального хранения документов детализирует архитектуру системы,
показывая её взаимодействие с внешним миром и внутреннюю логику
обработки данных. Во внешнем окружении система взаимодействует с тремя
основными группами участников: сотрудниками (бухгалтерами, юристами,
менеджерами), которые загружают документы и отправляют поисковые
запросы; корпоративными системами (ERP/CRM), которые могут автоматически
запрашивать данные через API; а также источниками документов (сканерами,
почтой, файловыми хранилищами), откуда документы поступают на хранение.
Процесс работы сервиса построен как конвейер обработки данных: документы
из внешних источников поступают напрямую в хранилище документов, а
сотрудники также могут загружать документы через модуль загрузки,
который сохраняет их в то же хранилище. Далее хранилище документов
передает файлы в модуль предобработки для подготовки изображений, после
чего очищенное изображение поступает в модуль OCR для распознавания
текста. Распознанный текст параллельно направляется в модули
классификации (для определения типа документа) и извлечения сущностей
(NER), а результаты их работы — тип документа и извлеченные поля —
сохраняются в структурированном хранилище. Затем данные из
структурированного хранилища передаются в модуль индексации, и
построенный поисковый индекс сохраняется обратно в структурированное
хранилище для обеспечения быстрого доступа. Пользовательские запросы
поступают через API-слой в модуль индексации, после чего найденные
результаты возвращаются через API сотруднику, а внешние системы
(ERP/CRM) также могут получать структурированные данные, обращаясь к
API. Инфраструктурно хранилище моделей обеспечивает актуальными версиями
ML-моделей модули OCR, классификации и NER, а система логирования и
мониторинга собирает метрики качества со всех этапов обработки для
контроля производительности.

Диаграмма потоков данных первого уровня для сервиса интеллектуального
хранения документов детализирует его внутреннюю архитектуру через
взаимодействие внешних потребителей, основных модулей и внешних
хранилищ.

Верхняя часть диаграммы выделяет внешних потребителей, где Сотрудник
обращается к сервису через пользовательский интерфейс, ERP/CRM выступает
как внешняя корпоративная система, автоматически направляющая запросы на
получение извлеченных данных, а Источники документов автоматически
поставляют документы в систему.

Центральная часть показывает модули сервиса, где API Gateway выступает
единой точкой входа, Модуль загрузки отвечает за прием файлов,
Предобработка улучшает качество изображений, OCR распознает текст,
Классификация определяет тип документа, NER извлекает ключевые сущности,
Индексация строит поисковые индексы, а Мониторинг и логирование
обеспечивает сбор метрик.

Нижняя часть диаграммы показывает внешние хранилища: S3 для исходных
файлов, PostgreSQL для структурированных данных и индексов, Хранилище
моделей для версионирования ML-моделей, а также Логи для
централизованного сбора записей.

Потоки данных организованы следующим образом: документы от внешних
источников поступают напрямую в S3 или через модуль загрузки. Далее
документ последовательно проходит этапы предобработки, OCR,
классификации и NER. Результаты обработки сохраняются в PostgreSQL и
передаются в индексацию. Пользовательские запросы на поиск поступают
через API Gateway в модуль индексации, который возвращает найденные
результаты.

Потоки данных:

- Обработка документа: документ поступает в S3, откуда читается для
  обработки. Модели загружаются из хранилища моделей. Результаты
  обработки сохраняются в PostgreSQL и индексируются.

- Поиск и доступ: пользователь запрашивает поиск, сервис обращается к
  индексу в PostgreSQL, получает результаты и возвращает их через API.

Модули системы и протоколы взаимодействия

- API Gateway — REST API (HTTP/JSON, multipart)

- Модуль загрузки — S3 API (HTTP) для записи в S3, Message Queue
  (RabbitMQ/Kafka) для запуска обработки

- Предобработка, OCR, Классификация, NER — синхронные вызовы
  (gRPC/REST) между модулями, чтение моделей по HTTP (S3 API/pre-signed
  URLs)

- Индексация — SQL (PgBouncer/прямое подключение) для работы с
  PostgreSQL, полнотекстовый поиск через PostgreSQL FTS

- Мониторинг — асинхронная отправка логов (UDP/Filebeat) или прямая
  запись в БД

| **Модуль** | **Ответственность** | **Входные данные** | **Выходные данные** | **Протокол взаимодействия** |
|------------|---------------------|--------------------|--------------------|----------------------------|
| **API Gateway** | Прием запросов от пользователей и внешних систем, маршрутизация, валидация, формирование ответов | HTTP-запрос (JSON: поиск; multipart: файл) | HTTP-ответ (JSON с результатами) | REST API (HTTP/1.1, HTTPS) — внешний; gRPC/REST — внутренние вызовы к модулям |
| **Модуль загрузки** | Прием файлов документов, сохранение в S3, инициирование обработки | Файл документа, метаданные | ID документа, подтверждение | S3 API (HTTP/2) — запись в S3; AMQP/Kafka — отправка события о новой загрузке |
| **Предобработка** | Улучшение качества изображений (поворот, обрезка, шум) | Изображение из S3 | Очищенное изображение | S3 API (HTTP) — чтение из S3; gRPC (бинарные данные) — передача в OCR |
| **OCR** | Распознавание текста с изображений | Очищенное изображение | Распознанный текст (строка) | HTTP (GET) — загрузка модели из хранилища (presigned URL); gRPC — передача текста в классификацию и NER |
| **Классификация** | Определение типа документа | Распознанный текст | Тип документа + confidence | HTTP (GET) — загрузка модели; PostgreSQL wire protocol (TCP) — запись результата в БД |
| **NER** | Извлечение ключевых сущностей | Распознанный текст | Структурированные поля (JSON) | HTTP (GET) — загрузка модели; PostgreSQL wire protocol — запись полей в БД |
| **Индексация** | Построение индекса, полнотекстовый поиск | Поисковый запрос или новые данные | Список документов, релевантность | PostgreSQL wire protocol — чтение/запись индекса (FTS); gRPC — ответ на поисковый запрос |
| **Мониторинг и логирование** | Сбор метрик (latency, CER, precision), логирование ошибок | События от всех модулей | Записи в логах, алерты | UDP/syslog или HTTP (Beats/Elastic) — асинхронная отправка событий; SQL — запись в БД логов |

**Выбор моделей:**

- OCR baseline: Tesseract (легковесный, открытый, большое сообщество).

- OCR основная: TrOCR (трансформер от Microsoft, высокая точность на
  печатном тексте) или EasyOCR.

- Классификация: ResNet18 (fine-tuned) — классическая CNN-архитектура для классификации изображений.

- NER: spaCy (продуктовая скорость, встроенная поддержка русскоязычных

  точности.

**Подход:**

Комбинированный пайплайн, где изображение проходит через предобработку
(OpenCV), затем OCR (Tesseract/TrOCR), после чего распознанный текст
подается в модели классификации и NER. Все этапы объединены в единый
DAG-пайплайн с логированием метрик на каждом шаге. Для исключения ошибок
распознавания используется пост-обработка на основе правил и регулярных
выражений.

| **OCR (распознавание текста)** | Tesseract + pytesseract / TrOCR | Tesseract — зрелый open-source OCR, работает с 100+ языками, прост в интеграции. TrOCR — SOTA для печатного текста, если есть GPU | EasyOCR: Хорош, но медленнее. Google Vision API: Платный, требует интернета. |
| **Классификация документов** | ResNet18 (fine-tuned) | ResNet — проверенная архитектура для классификации изображений. Fine-tuning позволяет достичь высокой точности на целевом датасете. | BERT/ruBERT: Избыточен, если основная информация заложена в визуальном образе документа. TF-IDF+SVM: Более слабый baseline. |
| **NER (извлечение сущностей)** | spaCy / transformers | spaCy — индустриальный стандарт, быстрый, есть русские модели. Transformers (HuggingFace) — максимальная гибкость и точность | CRF (sklearn-crfsuite): Устаревший подход, хуже качество. Правила вручную: Не масштабируется. |
| **Веб-фреймворк** | FastAPI | Высокая производительность (async), автодокументация, встроенная валидация Pydantic, простота интеграции с ML | Flask: Синхронный, медленнее под нагрузкой. Django: слишком тяжелый, избыточен. |
| **База данных (структуры)** | PostgreSQL + pgvector | Надёжность, поддержка JSON, полнотекстовый поиск (FTS), расширение pgvector для embeddings | MongoDB: Документо-ориентированная, но хуже с JOIN и ACID. MySQL: меньше возможностей для JSON. |
| **Файловое хранилище** | S3 (MinIO / Yandex Object Storage) | Промышленный стандарт для хранения объектов. HTTP-доступ, версионирование, дешевизна. MinIO поднимается локально в Docker | Локальная файловая система: не масштабируется, проблемы с бэкапами. HDFS: избыточно для задачи. |
| **Поисковый движок** | PostgreSQL FTS / Elasticsearch | PostgreSQL FTS — "из коробки", не требует отдельного сервиса. Elasticsearch — более мощный, кластеризуемый | Elasticsearch — выбор для продакшна, PostgreSQL — для простоты старта. |
| **Сериализация моделей** | joblib / pickle | joblib эффективен для моделей с numpy-массивами (scikit-learn). pickle — универсален для любых Python-объектов | ONNX: Избыточен, если не планируем менять фреймворк. TorchScript: только для PyTorch. |
| **Хранение данных (прототип)** | PostgreSQL + S3 | PostgreSQL для метаданных и индексов, S3 для исходных файлов | CSV/файлы: Непригодны для многопользовательской работы. SQLite: не держит конкурентную нагрузку. |
| **Хранение моделей** | MLflow Model Registry / S3 | MLflow версионирует модели, хранит метаданные экспериментов, имеет UI для сравнения. S3 хранит бинарные файлы | DVC: Хорош для данных, хуже для lifecycle моделей. Просто папка с датами: нет версионирования и метаданных. |
| **Логирование экспериментов** | MLflow Tracking | Логирует параметры (размер изображения, threshold), метрики (CER, precision), артефакты (примеры ошибок OCR) | TensorBoard: только для глубокого обучения. CSV + git: неудобно сравнивать. |
| **Мониторинг** | structlog + prometheus_client + Grafana | structlog для структурированных логов, prometheus для метрик (latency OCR, количество ошибок NER), Grafana для дашбордов | ELK: Тяжелее, требует больше ресурсов. Просто print: бесполезно для анализа. |
| **Протокол API** | REST (внешний) + gRPC (внутренний) | REST — стандарт для внешних систем, поддержка multipart. gRPC — быстрее, типизирован, потоковая передача для внутренних модулей | REST везде: медленные внутренние вызовы. gRPC везде: неудобен для загрузки файлов и внешней интеграции. |
| **Очереди задач** | Celery + Redis / RabbitMQ | Для асинхронной обработки длительных задач (OCR, NER). Redis как брокер и бэкенд результатов | Просто синхронная обработка: блокирует API, пользователь ждёт. Kafka: слишком мощная для задачи. |
| **Конфигурация** | YAML + pydantic-settings | YAML — читаем, поддерживает комментарии. Pydantic — валидация типов, автодополнение в IDE | JSON: нет комментариев. .env: Только для строк, не структурирован |
| **Воспроизводимость** | Docker + docker-compose + requirements.txt | Docker изолирует окружение, docker-compose поднимает связанные сервисы (PostgreSQL, MinIO, Redis) | Conda: Тяжелее, чем Docker. Poetry: Хорош, но для лабораторной работы requirements.txt проще. |
