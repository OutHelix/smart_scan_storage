## 1. Стратегия валидации и воспроизводимость

### 1.1. Детальная стратегия валидации

#### 1.1.1. Природа данных и её влияние на валидацию

В проекте используются два основных источника данных, каждый из которых предъявляет специфические требования к валидации:

- **RVL-CDIP** — содержит 400 000 изображений, разделённых на 16 классов документов (счета, договоры, письма, формы и др.). Каждый документ представлен одним изображением, что технически упрощает разбиение на обучающую и тестовую выборки. Однако этот датасет не отражает многолистовую природу реальных документов, где один логический документ может занимать несколько страниц.

- **FUNSD** — содержит 199 отсканированных форм с аннотациями сущностей на уровне слов и bounding boxes. Каждая форма содержит десятки аннотированных элементов (даты, суммы, названия организаций). Аннотации привязаны к форме как к целостному объекту, поэтому разбиение на уровне отдельных слов или предложений приведёт к тому, что одна и та же форма окажется одновременно в train и test, что является критической утечкой данных.

**Особенность реального сценария**: в промышленной эксплуатации документы (договоры, акты, отчёты) часто состоят из нескольких страниц, которые сканируются как отдельные файлы или объединяются в PDF. Страницы одного логического документа не должны попадать в разные выборки (train/test), иначе модель получит нечестное преимущество, увидев часть документа на обучении и экстраполируя знания на тестовую страницу.

**Вывод для стратегии валидации**: необходимо использовать группировку по идентификатору документа при формировании сплитов, чтобы все страницы одного документа оставались в пределах одной выборки. Для RVL-CDIP группировка избыточна, но должна быть реализована для единообразия пайплайна. Для FUNSD группировка является обязательным требованием, без которого корректная оценка качества NER невозможна.

**Пример реализации**:
```python
from sklearn.model_selection import StratifiedGroupKFold

sgkf = StratifiedGroupKFold(n_splits=5)
for fold, (train_idx, val_idx) in enumerate(sgkf.split(X, y, groups=document_ids)):
    # Все страницы одного документа попадают либо в train, либо в val
    train_docs = X.iloc[train_idx]
    val_docs = X.iloc[val_idx]
```

**Дополнительные меры**:

- Фиксированный тестовый набор объёмом 20% документов выделяется на начальном этапе до проведения кросс-валидации. Этот набор полностью исключается из процессов подбора гиперпараметров и обучения финальной модели, что позволяет получить объективную оценку качества на данных, не участвовавших ни в каком виде в обучении.

- Тестовый набор формируется с использованием тех же принципов, что и валидационные фолды: сохраняется стратификация по классам документов и группировка по идентификатору документа. Это гарантирует, что пропорции редких классов в тестовой выборке соответствуют реальному распределению, а все страницы одного документа остаются в пределах одной выборки.

#### 1.1.3. Стратегия для NER (извлечение сущностей)

**Метод**: групповая кросс-валидация с разбиением по документам (GroupKFold).

**Обоснование**: 
- В датасете FUNSD одна форма содержит десятки сущностей. Если разбивать на уровне предложений или токенов, одна и та же форма окажется и в train, и в test.
- Это приводит к завышению метрик на 10–20% в зависимости от типа сущности, так как модель фактически запоминает разметку конкретных документов, а не обучается обобщению.

**Пример реализации**:
```python
from sklearn.model_selection import GroupKFold

gkf = GroupKFold(n_splits=5)
for train_idx, val_idx in gkf.split(tokens, labels, groups=document_ids):
    # Все сущности одного документа целиком в одной выборке
    train_tokens = tokens[train_idx]
    val_tokens = tokens[val_idx]
```

**Метрики**: используются микро и макро-усреднённые precision, recall, F1-score. Микро-усреднение даёт оценку качества на уровне отдельных сущностей и чувствительно к частотности типов. Макро-усреднение позволяет оценить, как модель справляется с каждым типом сущности независимо от его распространённости. Для редких сущностей (например, «сумма в евро», «ИНН») дополнительно отслеживаются метрики по каждому типу для выявления дисбаланса и принятия решения о необходимости дообучения на синтетических примерах.

#### 1.1.4. Стратегия для OCR (распознавание текста)

**Метод**: валидация на специально сформированном тестовом наборе с ручной верификацией эталонного текста.

**Обоснование**: 
- OCR-модели оцениваются по CER и WER, которые требуют точного совпадения распознанного текста с эталоном. Автоматическая валидация на синтетически сгенерированных данных не отражает реальные искажения, присутствующие в промышленных сканах: геометрические перекосы, размытие при движении документа, пятна и заливки, низкое разрешение (менее 200 dpi), а также артефакты сжатия.
- Различные OCR-движки демонстрируют разные паттерны ошибок. TrOCR (трансформерная архитектура) лучше справляется с печатным текстом стандартных шрифтов, но может галлюцинировать (добавлять несуществующие слова) на зашумлённых изображениях. Tesseract более консервативен, но чаще ошибается в распознавании специфических шрифтов и таблиц. Поэтому оценка должна проводиться на едином тестовом наборе для корректного сравнения моделей.

**Формирование тестового набора**:
1. Отбирается 500 документов из всех типов (счета, договоры, акты, формы и др.) с учётом баланса классов, чтобы оценить качество распознавания на каждом типе документа.
2. Для каждого документа вручную выверяется эталонный текст. Если доступен исходный текст из PDF (например, для документов, созданных электронно), он используется после проверки соответствия визуальному отображению. Для сканов без исходного текста выполняется ручная транскрипция.
3. В набор целенаправленно включаются документы с низким качеством сканирования: разрешение менее 150 dpi, сильный шум (зернистость), перекос более 5 градусов, наличие заливок или печатей, перекрывающих текст. Это позволяет оценить устойчивость моделей к реальным дефектам.

**Метрики и пороговые значения**:
- **CER (Character Error Rate)** — вычисляется по формуле Левенштейна как отношение минимального количества операций вставки, удаления и замены символов к общей длине эталонной строки. Позволяет оценить точность распознавания на уровне отдельных символов, что критично для цифр в суммах и датах.
- **WER (Word Error Rate)** — аналогичная метрика на уровне слов. Более релевантна для оценки читаемости текста и пригодности его для downstream-задач (классификация, NER), так как ошибка в одном символе может не нарушить понимание слова.

**Пример расчёта CER**:
```python
def calculate_cer(reference, hypothesis):
    import Levenshtein
    distance = Levenshtein.distance(reference, hypothesis)
    return distance / len(reference)
```

**Пороговые значения**:
- **CER < 5%** — модель пригодна для полностью автоматической обработки без ручной проверки. Допустимы единичные ошибки в незначимых символах.
- **CER 5–15%** — требуется пост-обработка (например, исправление на основе правил или словаря) либо ручная проверка критических полей (суммы, даты, ИНН). Основной текст может использоваться для поиска с учётом возможных опечаток.
- **CER > 15%** — модель требует дообучения на данных с аналогичными характеристиками или замены на более подходящую архитектуру. Автоматическое использование таких результатов недопустимо.

#### 1.1.5. Сводная таблица стратегий валидации

| Задача | Метод валидации | Группировка | Количество фолдов | Тестовая выборка |
|--------|----------------|-------------|-------------------|------------------|
| Классификация | StratifiedGroupKFold | document_id | 5 | 20%, фиксированный |
| NER | GroupKFold | document_id | 5 | 20%, фиксированный |
| OCR | Фиксированный тестовый набор с ручной верификацией | не применимо | не применимо | 500 документов |

**Пояснения к таблице**:

- **Классификация** использует стратифицированную групповую кросс-валидацию, что позволяет одновременно сохранять пропорции классов (стратификация) и предотвращать утечку между страницами одного документа (группировка). 5 фолдов выбрано как компромисс между достаточным объёмом валидационных данных и вычислительными затратами. Фиксированный тестовый набор в 20% выделяется до начала экспериментов и не участвует ни в подборе гиперпараметров, ни в обучении финальной модели.

- **NER** применяет групповую кросс-валидацию без стратификации, так как стратификация на уровне документов в задаче извлечения сущностей технически сложна (один документ содержит несколько типов сущностей) и может нарушить целостность разметки. Группировка по document_id является критически важной: все сущности одного документа должны оставаться в пределах одной выборки, иначе модель будет запоминать разметку конкретных форм, а не обобщать.

- **OCR** оценивается на специально сформированном тестовом наборе, а не в рамках кросс-валидации, по следующим причинам:
  - Оценка требует ручной верификации эталонного текста, что трудоёмко для больших объёмов.
  - OCR-модель обычно не обучается на целевых данных (используется предобученная или дообученная на независимых датасетах), поэтому кросс-валидация не имеет смысла.
  - Тестовый набор из 500 документов обеспечивает статистическую значимость при оценке CER и WER, покрывает все типы документов и включает пограничные случаи (низкое качество сканов, перекосы).

### 1.2. Воспроизводимость экспериментов

#### 1.2.1. Версионирование данных

Для воспроизводимости экспериментов необходимо фиксировать не только код, но и данные, на которых обучаются модели. Без этого невозможно гарантировать, что через месяц или год при повторном запуске будут получены те же результаты. Используется **DVC (Data Version Control)** в связке с S3-совместимым хранилищем (MinIO для локальной разработки, Yandex Object Storage или AWS S3 для production).

**Принцип работы DVC**: 
- DVC создаёт метафайлы (с расширением `.dvc`), которые хранятся в Git и содержат хэши данных и ссылки на удалённое хранилище.
- Сами данные (изображения, аннотации) хранятся в S3 и не загружаются в Git, что позволяет работать с большими объёмами (сотни гигабайт) без раздувания репозитория.
- При переключении между коммитами Git команда `dvc pull` автоматически загружает соответствующую версию данных.

**Структура хранения**:

```
project/
├── data/
│   ├── raw/                 # исходные датасеты в неизменном виде
│   │   ├── RVL-CDIP/        # 400k изображений
│   │   └── FUNSD/           # 199 форм с аннотациями
│   ├── processed/           # данные после предобработки
│   │   ├── images/          # нормализованные изображения (единый формат, размер)
│   │   └── annotations/     # разметка в едином формате JSON (COCO-подобная структура)
│   └── test_set/            # фиксированный тестовый набор (20% документов)
│       ├── images/
│       └── ground_truth/    # эталонные тексты для OCR, метки для классификации и NER
├── data.dvc                 # DVC-файл для raw данных
└── processed.dvc            # DVC-файл для processed данных
```

**Обоснование структуры**:
- **`raw/`** хранится в неизменном виде — это «источник истины». Любые преобразования выполняются в процессе обработки, что позволяет при необходимости перестроить processed-данные с другими параметрами предобработки.
- **`processed/`** содержит данные в формате, готовом для загрузки в ML-модели. Единый формат JSON для аннотаций упрощает код обучения: не требуется писать отдельные парсеры для RVL-CDIP и FUNSD.
- **`test_set/`** фиксируется и не изменяется между экспериментами, что обеспечивает сопоставимость результатов при сравнении разных версий моделей. Этот набор выделяется один раз до начала экспериментов и хранится отдельно от кросс-валидационных фолдов.

**Пример DVC-файла (data/raw.dvc)**:
```yaml
md5: 8a7b9c3d4e5f6a7b8c9d0e1f2a3b4c5d
outs:
  - md5: 1a2b3c4d5e6f7a8b9c0d1e2f3a4b5c6d.dir
    path: data/raw
    cache: true
```

**Рабочий процесс**:
1. При добавлении нового датасета или изменении существующего: `dvc add data/raw`
2. Фиксация изменений в Git: `git add data/raw.dvc && git commit`
3. Выгрузка данных в удалённое хранилище: `dvc push`
4. На другой машине или при восстановлении окружения: `dvc pull` (загружает актуальную версию данных, соответствующую текущему коммиту Git)

#### 1.2.2. Версионирование кода

Используется Git с политикой ветвления:
- `main` — стабильная версия, готовая к деплою.
- `develop` — интеграционная ветка.
- `experiment/<name>` — ветки для конкретных экспериментов.

#### 1.2.3. Версионирование моделей и экспериментов

**Инструмент**: MLflow Model Registry.

MLflow используется как централизованное хранилище для управления жизненным циклом моделей. Model Registry обеспечивает версионирование, переход моделей между стадиями (Staging, Production, Archived) и хранение всех артефактов, связанных с экспериментом.

**Схема хранения**:
- Каждый эксперимент (например, «дообучение TrOCR на RVL-CDIP») имеет уникальный ID. Эксперименты группируются по задачам: `ocr_experiments`, `classification_experiments`, `ner_experiments`.
- В рамках одного run (запуска) логируются:
  - **Гиперпараметры**: learning rate, batch size, архитектура модели, параметры аугментации.
  - **Метрики**: CER, WER, precision, recall, F1-score на валидации (по эпохам или шагам).
  - **Артефакты**: веса модели (в формате .pt, .pkl), конфигурационные файлы, примеры ошибок (для последующего анализа).
  - **Контекстная информация**: версия данных (хэш DVC), хэш коммита Git, версия окружения (pip freeze).

**Пример логирования эксперимента**:
```python
import mlflow
import subprocess

with mlflow.start_run(run_name="ocr_trocr_finetune"):
    # Логирование гиперпараметров
```

**Работа с чекпоинтами при длительном обучении**:
Если обучение занимает несколько дней (например, дообучение TrOCR на 400k изображений), используются чекпоинты — сохранение весов модели каждые N эпох или по расписанию. MLflow позволяет логировать промежуточные метрики, а сам чекпоинт сохраняется как артефакт с указанием шага:
```python
if epoch % 5 == 0:
    mlflow.pytorch.log_model(model, f"checkpoint_epoch_{epoch}")
```
При сбое инфраструктуры или прерывании эксперимента обучение может быть возобновлено с последнего сохранённого чекпоинта, а не с начала. Это критически важно для экономии вычислительных ресурсов и времени.

**Стадии моделей в Registry**:
- **Staging** — модель прошла валидацию на тестовом наборе, но ещё не утверждена для production. Используется для A/B-тестирования и дополнительной проверки.
- **Production** — модель развёрнута в промышленной среде и обрабатывает реальный трафик.
- **Archived** — устаревшая версия, сохранённая для возможности отката.
Переход между стадиями выполняется через UI MLflow или через API, что позволяет автоматизировать процесс в CI/CD пайплайне.

#### 1.2.4. Версионирование окружения

Для обеспечения полной воспроизводимости недостаточно зафиксировать код и данные — необходимо также контролировать окружение, в котором выполняются обучение и инференс. Окружение фиксируется на трёх уровнях:

**1. requirements.txt** — точные версии Python-библиотек с хэшами для защиты от supply chain атак.
```
torch==2.1.0 --hash=sha256:...
transformers==4.36.0
fastapi==0.104.1
celery==5.3.4
redis==5.0.1
```
Использование точных версий (без операторов `>=` или `~=`) гарантирует, что при повторной установке будут получены те же зависимости. Дополнительно может использоваться `poetry.lock` или `pip-tools` для более строгого контроля транзитивных зависимостей.

**2. Docker-образы** — для каждого сервиса создаётся образ с уникальным тегом, включающим версию модели и дату сборки. Это позволяет однозначно идентифицировать, какая версия кода и моделей развёрнута в конкретный момент.
```

classifier-service:v2.1.0-20250324
```

## 2. Анализ утечек данных

### 2.1. Категории утечек и способы предотвращения

#### 2.1.1. Утечка на уровне страниц документа

**Описание риска**: 
В реальных условиях документы (договоры, акты, отчёты) часто состоят из нескольких страниц. При подготовке данных эти страницы могут быть представлены как отдельные изображения (при сканировании) или извлечены из многостраничного PDF. Если при разбиении на обучающую и тестовую выборки не учитывать принадлежность страниц к одному документу, возникает классическая утечка данных: одна страница попадает в train, другая — в test. Модель, увидев часть документа (например, первую страницу договора) на обучении, получает возможность экстраполировать знания о структуре, шрифтах, логотипах и даже специфическом содержимом на тестовую страницу того же документа. Это приводит к нереалистично высоким метрикам, которые не отражают реальную способность модели обобщаться на новые, невиданные ранее документы.

**Реальный пример утечки**:
- Документ: договор из 3 страниц.
- Страница 1 (содержит название организации и общие условия) попадает в train.
- Страница 2 (содержит ту же организацию и специфические пункты) попадает в test.
- Модель классификации, увидев на обучении страницу 1, запоминает визуальные признаки (логотип, расположение реквизитов) и текстовые паттерны (формулировки договора). На тесте она с высокой вероятностью правильно классифицирует страницу 2, но это не является честным результатом — модель не обобщалась на новый документ, а просто узнала знакомые признаки.

**Предотвращение**: 
При формировании сплитов используется группировка по уникальному идентификатору документа (`document_id`). Все страницы, принадлежащие одному документу, должны попадать исключительно в одну выборку (либо все в train, либо все в test, либо все в валидацию). Это требование распространяется на все этапы: выделение тестового набора, кросс-валидацию и любые последующие разбиения.

**Пример корректного разбиения**:
```python
def create_splits(documents, test_size=0.2, random_state=42):
    """
    Разбиение на train/test на уровне документов, а не страниц.
    
    Args:
        documents: DataFrame с колонками document_id, page_num, features
        test_size: доля документов в тестовой выборке
    
    Returns:
        train, test: DataFrames с сохранённой структурой страниц
    """
    # Получаем уникальные идентификаторы документов
    unique_docs = documents['document_id'].unique()
    
    # Разбиваем идентификаторы, а не страницы
    train_docs, test_docs = train_test_split(
        unique_docs, 
        test_size=test_size, 
        random_state=random_state,
        stratify=documents.groupby('document_id')['class'].first()  # стратификация по классу
    )
    
    # Фильтруем исходный DataFrame по идентификаторам
    train = documents[documents['document_id'].isin(train_docs)]
    test = documents[documents['document_id'].isin(test_docs)]
    
    return train, test
```

**Важные детали реализации**:
- Стратификация выполняется по классу документа, который берётся из первой страницы (или агрегируется, если класс определён на уровне документа). Это сохраняет пропорции редких классов.
- Для кросс-валидации следует использовать `StratifiedGroupKFold` или `GroupKFold` из scikit-learn, передавая `document_id` в параметр `groups`.
- При работе с датасетами типа RVL-CDIP, где каждый файл уже является отдельным документом, группировка избыточна, но для единообразия пайплайна идентификатором выступает имя файла.
- В логах и метриках необходимо фиксировать, на каком уровне выполнялось разбиение (документный или страничный), чтобы избежать путаницы при сравнении экспериментов.

#### 2.1.2. Утечка через метаданные

**Описание риска**:
Метаданные, сопровождающие документы, часто несут информацию, напрямую связанную с целевыми переменными. В реальных системах документы поступают с именами файлов, путями в файловой системе, датами загрузки, идентификаторами пользователей, источниками (email, сканер, API) — и всё это может стать неявными признаками, которые модель научится использовать вместо реального содержания документа.

**Конкретные примеры утечек**:

| Тип метаданных | Пример | Чем опасен |
|----------------|--------|------------|
| Имя файла | `invoice_2023_03_15.pdf`, `contract_ABC_LLC.pdf` | Напрямую содержит тип документа или название организации |
| Путь к папке | `/scans/contracts/2024/`, `/invoices/processed/` | Каталог явно указывает класс документа |
| Дата загрузки | 30.03.2025 | Счета чаще загружаются в конце месяца, договоры — равномерно |
| Источник | `email: accounting@company.ru` | Определённые отправители ассоциированы с конкретными типами документов |
| Имя пользователя | `uploaded_by: legal_department` | Юридический отдел загружает договоры, бухгалтерия — счета |
| Размер файла | 2.3 MB | Договоры обычно длиннее счетов, размер может быть коррелирован с классом |
| MIME-тип | `application/pdf` против `image/jpeg` | Разные типы файлов могут преобладать в разных классах |

**Почему это проблема**:
Если модель получает доступ к таким метаданным, она может достичь высокой точности на тестовой выборке, не научившись анализировать реальное содержание документа. В production, когда новые документы будут поступать с произвольными именами (например, `scan_001.pdf`), модель окажется бесполезной, так как опиралась на признаки, которые не являются устойчивыми.

**Предотвращение**:
Все метаданные, не являющиеся частью содержания документа, исключаются из набора признаков для ML-моделей. Модели классификации и NER получают только:
- Распознанный текст документа (после OCR)
- Опционально: изображение документа (для CNN-классификаторов или multi-modal подходов)

Метаданные могут использоваться только для:
- Маршрутизации запросов на уровне API
- Фильтрации результатов поиска (например, поиск только по документам, загруженным после определённой даты)
- Аудита и логирования

Они **не должны** передаваться в модель как входные признаки.

**Пример**:
```python
# Список колонок, которые содержат метаданные и должны быть исключены
metadata_columns = [
    'filename', 
    'filepath', 
    'upload_date', 
    'source', 
    'user_id', 
    'file_size', 
    'mime_type',
    'folder_structure'
]

# Исключение на этапе подготовки данных
X_train = X_train.drop(columns=metadata_columns, errors='ignore')
X_test = X_test.drop(columns=metadata_columns, errors='ignore')
```

**Дополнительные меры**:
- При формировании датасетов для обучения следует избегать включения метаданных в разметку. Если исходные данные содержат такие поля, они должны быть явно удалены перед передачей в пайплайн.
- В конфигурации эксперимента фиксируется, какие поля были исключены, чтобы при воспроизведении результат не изменился.
- При использовании предобученных моделей (например, BERT для классификации) важно убедиться, что в токенизатор не попадают случайно метаданные, вшитые в текст (например, если текст извлекался вместе с колонтитулами, содержащими дату и имя файла).

#### 2.1.3. Утечка при предобработке

**Описание риска**:
Предобработка данных часто включает операции, требующие вычисления статистик по выборке: нормализация (вычитание среднего и деление на стандартное отклонение), масштабирование признаков, определение параметров для выравнивания гистограммы, расчёт коэффициентов для коррекции геометрических искажений. Если эти параметры вычисляются на всём датасете **до** разделения на train и test, информация из тестовой выборки неявно используется при обучении модели. Это классическая форма утечки данных, которая приводит к завышению метрик, так как модель получает представление о распределении тестовых данных.

**Конкретные примеры**:

| Тип предобработки | Пример утечки | Последствия |
|-------------------|---------------|-------------|
| Нормализация изображений | Вычисление среднего яркости и стандартного отклонения по всем изображениям, затем нормализация | Модель «видит» общее распределение тестовых изображений, метрики завышаются на 1–5% |
| Стандартизация признаков | Масштабирование числовых признаков (например, размер документа) с использованием глобальных mean и std | Модель обучается на данных, уже смещённых к распределению теста |
| Выравнивание гистограммы | Определение параметров CLAHE (ограниченное адаптивное выравнивание гистограммы) на всём наборе | Параметры подбираются с учётом контрастности тестовых изображений |
| Удаление выбросов | Идентификация и удаление аномалий на основе квантилей всего датасета | Тестовые выбросы могут быть удалены до обучения, хотя в реальности они присутствуют |
| Заполнение пропусков | Использование медианы или среднего, вычисленного по всему датасету | В тестовые данные внедряется информация из обучающей выборки |

**Почему это критично**:
В реальном эксплуатационном сценарии система не имеет доступа к распределению будущих данных. Модель должна обобщаться на новые документы, основываясь только на том, что она «увидела» в обучающей выборке. Если предобработка использует статистики теста, создаётся иллюзия более высокого качества, которая исчезает при внедрении системы.

**Предотвращение**:
Все параметры предобработки вычисляются исключительно на обучающей выборке и сохраняются для применения к тестовой (и к любым новым данным в production). Это реализуется через объекты-трансформеры с методами `fit()` и `transform()` (или `fit_transform()`), аналогично интерфейсу scikit-learn.

**Пример корректной реализации**:
```python
import numpy as np
from sklearn.base import BaseEstimator, TransformerMixin

class ImageNormalizer(BaseEstimator, TransformerMixin):
    """Нормализация изображений с сохранением статистик из train."""
    
    def fit(self, images, y=None):
        """
        Вычисляет среднее и стандартное отклонение на обучающей выборке.
        """
        self.mean_ = np.mean(images, axis=(0, 1, 2), keepdims=True)
        self.std_ = np.std(images, axis=(0, 1, 2), keepdims=True)
        return self
    
    def transform(self, images):
        """
        Применяет сохранённые статистики для нормализации.
        """
        return (images - self.mean_) / (self.std_ + 1e-8)

# Использование в пайплайне
normalizer = ImageNormalizer()
normalizer.fit(train_images)           # статистики только по train
train_norm = normalizer.transform(train_images)
test_norm = normalizer.transform(test_images)  # те же статистики
```

**Дополнительные меры**:
- В пайплайне scikit-learn все трансформеры должны быть включены в `Pipeline`, который автоматически вызывает `fit()` только на train при использовании `cross_val_score` или `GridSearchCV`.
- При использовании глубокого обучения (PyTorch/TensorFlow) статистики нормализации часто вычисляются на train и фиксируются как константы. Например, для ImageNet используются предопределённые mean и std, а не вычисленные на целевом датасете.
- Для геометрических преобразований (поворот, выравнивание) параметры (угол поворота, матрица преобразования) должны вычисляться на каждом изображении независимо, без использования глобальных статистик.
- В логах эксперимента фиксируется, какие статистики использовались для предобработки и на каком объёме данных они вычислялись, что позволяет воспроизвести результат.

#### 2.1.4. Утечка через аугментацию

**Описание риска**:
Аугментация данных — это процесс искусственного расширения обучающей выборки путём применения случайных преобразований к исходным изображениям (повороты, сдвиги, масштабирование, добавление шума, изменение яркости и контрастности). Если аугментация применяется ко всем данным **до** разделения на train и test, возникает риск, что аугментированные копии документов из тестовой выборки окажутся в обучающей. Даже если аугментация применяется после разделения, но к валидационной выборке, метрики на валидации перестают быть объективными, так как модель видит искажённые версии тех же документов.

**Конкретные примеры утечек**:

| Сценарий | Описание | Последствия |
|----------|----------|-------------|
| Аугментация до сплита | Применение `RandomRotation` ко всему датасету, затем разделение на train/test | Аугментированная версия тестового документа может попасть в train |
| Аугментация на валидации | Валидационная выборка проходит через те же трансформации, что и train | Модель оценивается на искажённых данных, метрики не отражают реальное качество |
| Стохастические трансформации без фиксации seed | При каждом запуске генерируются разные аугментации, даже для валидации | Результаты невоспроизводимы, сравнение экспериментов некорректно |
| Применение аугментации к тексту | Синонимические замены, перестановка слов в тексте для NER | Искажается структура документа, метки сущностей могут стать некорректными |

**Почему это критично**:
Цель аугментации — сделать модель устойчивой к вариативности входных данных, не меняя при этом распределение тестовой выборки. Валидационная и тестовая выборки должны оставаться в исходном, «естественном» виде, чтобы метрики отражали реальную способность модели работать с немодифицированными документами. Если валидация проходит на аугментированных данных, невозможно отличить улучшение обобщающей способности модели от простой адаптации к конкретному набору трансформаций.

**Предотвращение**:
Аугментация применяется **исключительно** к обучающей выборке. Валидационная и тестовая выборки проходят только через минимальные обязательные преобразования (приведение к единому формату, нормализацию, преобразование в тензор).

**Пример корректной реализации в PyTorch**:
```python
from torchvision import transforms

# Трансформации для обучения (с аугментацией)
train_transform = transforms.Compose([
    transforms.RandomRotation(degrees=5),           # случайный поворот до 5 градусов
    transforms.RandomAffine(                        # случайный сдвиг
        degrees=0, 
        translate=(0.05, 0.05)
    ),
    transforms.ColorJitter(                         # изменение яркости и контраста
        brightness=0.1, 
        contrast=0.1
    ),
    transforms.ToTensor(),                          # преобразование в тензор
    transforms.Normalize(mean=[0.485, 0.456, 0.406],  # нормализация ImageNet
                         std=[0.229, 0.224, 0.225])
])

# Трансформации для валидации и теста (без аугментации)
val_transform = transforms.Compose([
    transforms.ToTensor(),
    transforms.Normalize(mean=[0.485, 0.456, 0.406],
                         std=[0.229, 0.224, 0.225])
])

# При создании DataLoader
train_dataset = DocumentDataset(images, transform=train_transform)
val_dataset = DocumentDataset(images, transform=val_transform)
test_dataset = DocumentDataset(images, transform=val_transform)
```

**Дополнительные меры**:
- При использовании библиотек, которые применяют аугментацию на лету (например, Albumentations), необходимо убедиться, что для валидации и теста используется отдельный пайплайн без стохастических трансформаций.
- Для обеспечения воспроизводимости следует фиксировать seed для всех генераторов случайных чисел, используемых в аугментации. Это гарантирует, что при повторном запуске обучения будут применены те же самые аугментации.
- В логах эксперимента фиксируется список применённых аугментаций и их параметры, что позволяет оценить их влияние на итоговое качество модели.
- Для NER и классификации текста аугментация (синонимические замены, back-translation) применяется с осторожностью, так как может нарушить структуру документа или изменить смысл. Если текстовая аугментация используется, она также должна применяться только к train.

#### 2.1.5. Утечка через OCR-модель

**Описание риска**:
OCR-модель является первым этапом пайплайна: она преобразует изображение в текст, который затем используется классификатором и NER-моделью. Если OCR-модель была обучена или дообучена на документах, которые впоследствии попадают в тестовую выборку downstream-задач, возникает опосредованная утечка. Модели классификации и NER получают текст, распознанный с помощью модели, уже «знакомой» с этими документами, что приводит к завышению метрик.

**Конкретные сценарии**:
- Дообучение OCR на целевом корпусе (RVL-CDIP, FUNSD), который затем используется для обучения классификатора.
- Использование одного датасета и для OCR, и для downstream-задач.
- Fine-tuning OCR на документах, которые позже войдут в тест классификатора.

**Предотвращение**:

1. **Независимые датасеты**: OCR-модель обучается на публичных OCR-датасетах (SROIE, ICDAR, синтетические данные), не пересекающихся с целевыми документами. Если выполняется дообучение, используется отдельный набор, исключённый из downstream-выборок.

2. **Фиксация версии**: Версия OCR-модели жёстко фиксируется в MLflow Model Registry. Все downstream-эксперименты явно указывают, какая версия использовалась.

**Пример фиксации версии**:
```python
# Загрузка фиксированной версии OCR из Model Registry
model_uri = "models:/ocr_model/v1.0.0"
ocr_model = mlflow.pytorch.load_model(model_uri)

# Логирование версии в эксперименте классификатора
with mlflow.start_run():
    mlflow.log_param("ocr_model_version", "v1.0.0")
    text = ocr_model.predict(image)
```

3. **Разделение экспериментов**: Улучшения OCR проводятся изолированно. Переход на новую версию требует переобучения всех downstream-моделей.

4. **Аудит**: В MLflow для каждого downstream-эксперимента логируется версия OCR-модели, что обеспечивает воспроизводимость.

### 2.2. Матрица рисков

| Риск | Вероятность | Влияние | Способ предотвращения |
|------|-------------|---------|------------------------|
| Страницы одного документа в разных сплитах | Высокая | Критическое | Группировка по document_id при формировании сплитов; использование StratifiedGroupKFold |
| Метаданные как признаки | Средняя | Высокое | Исключение всех метаданных (имя файла, путь, дата, источник) из признакового пространства |
| Предобработка до сплита | Средняя | Среднее | Вычисление параметров (нормализация, масштабирование) только на train; применение к test без подгонки |
| Аугментация на val/test | Низкая | Среднее | Применение аугментаций (повороты, сдвиги, шум) только к train; val/test — только базовые преобразования |
| OCR видела тестовые документы | Низкая | Критическое | Обучение OCR на независимых датасетах; фиксация версии OCR-модели в MLflow для всех downstream-экспериментов |

**Пояснения к матрице**:

- **Вероятность** оценивает, насколько часто риск может проявиться при типичном процессе разработки без специальных мер контроля.
- **Влияние** определяет степень завышения метрик и искажения оценки качества модели:
  - *Критическое* — делает невозможной объективную оценку, требует полного пересмотра экспериментов.
  - *Высокое* — приводит к значительному завышению метрик (10–30%), скрывает реальные проблемы модели.
  - *Среднее* — завышение метрик в пределах 5–15%, может быть скорректировано при повторном обучении.
- Для каждого риска в столбце «Способ предотвращения» указаны конкретные технические меры, реализуемые на этапе подготовки данных и настройки экспериментов.

## 3. Масштабирование

### 3.1. Оценка нагрузки

#### 3.1.1. Профиль использования

Система обслуживает два основных сценария:

- **Загрузка документов** — пользователь или внешняя система отправляет файл. Это тяжёлая операция, включающая OCR, классификацию и NER.
- **Поиск и получение данных** — пользователь ищет документы по тексту или метаданным; внешние системы (ERP/CRM) запрашивают структурированные данные. Это лёгкие операции чтения.

**Оценка RPS (requests per second)**:

| Сценарий | Средний RPS | Пиковый RPS | Обоснование |
|----------|-------------|-------------|-------------|
| Загрузка документов | 0.5–1 | 10–20 | Массовая загрузка в начале дня или после выходных |
| Поиск | 10–20 | 100 | Активный поиск в рабочее время, скачки при отчётности |
| API для ERP/CRM | 5–10 | 50 | Пакетные запросы от интегрированных систем |

Суммарная нагрузка: в среднем 15–30 RPS, в пике до 120–170 RPS.

#### 3.1.2. Требования к задержкам (latency)

| Сценарий | Допустимая latency | Причина |
|----------|-------------------|---------|
| Загрузка (синхронно) | < 2 сек | Пользователь ожидает подтверждения |
| Загрузка (асинхронно) | < 30 сек | Пользователь получает task_id и проверяет позже |
| Поиск | < 500 мс | Критично для UX |
| API для ERP/CRM | < 1 сек | Требования SLA интеграции |

### 3.2. Подходы к масштабированию

#### 3.2.1. Асинхронная обработка с очередями задач

Для обработки документов используется паттерн «асинхронный инференс»: при загрузке система возвращает идентификатор задачи, а обработка выполняется в фоне.

**Пример определения задачи**:
```python
from celery import Celery

app = Celery('tasks', broker='redis://redis:6379/0')

@app.task(bind=True, max_retries=3)
def process_document(self, document_id, s3_path):
    try:
        text = ocr_model.predict(s3_path)
        doc_type = classifier.predict(text)
        entities = ner_model.predict(text)
        save_to_postgres(document_id, text, doc_type, entities)
    except Exception as e:
        self.retry(exc=e, countdown=60 * (2 ** self.request.retries))
```

**Пример эндпоинта загрузки**:
```python
@app.post("/upload")
async def upload_document(file: UploadFile):
    s3_path = await upload_to_s3(file)
    task = process_document.delay(s3_path)
    return {"task_id": task.id}
```

#### 3.2.2. Кеширование

Кеширование применяется на нескольких уровнях для снижения latency.

**Пример кеширования OCR**:
```python
import hashlib
import redis

redis_client = redis.Redis(host='redis', port=6379, db=2)

def get_or_compute_ocr(image_bytes):
    image_hash = hashlib.md5(image_bytes).hexdigest()
    cache_key = f"ocr:{image_hash}"
    
    cached = redis_client.get(cache_key)
    if cached:
        return cached.decode('utf-8')
    
    text = ocr_model.predict(image_bytes)
    redis_client.setex(cache_key, 60*60*24*30, text)  # 30 дней
    return text
```

#### 3.2.3. Горизонтальное масштабирование сервисов

Архитектура построена как набор микросервисов, каждый из которых масштабируется независимо.

**Пример конфигурации Horizontal Pod Autoscaler в Kubernetes**:
```yaml
apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata:
  name: ocr-hpa
spec:
  scaleTargetRef:
    kind: Deployment
    name: ocr-service
  minReplicas: 2
  maxReplicas: 20
  metrics:
  - type: Resource
    resource:
      name: cpu
      target:
        type: Utilization
        averageUtilization: 70
```

#### 3.2.4. Оптимизация задержек (latency)

Для снижения времени ответа применяются следующие методы:

- **Прогрев моделей при старте** — все модели загружаются в память на этапе инициализации сервиса.

**Пример прогрева моделей в FastAPI**:
```python
from fastapi import FastAPI

app = FastAPI()

@app.on_event("startup")
async def load_models():
    global ocr_model, classifier, ner_model
    ocr_model = torch.load("models/ocr.pt", map_location='cuda')
    classifier = joblib.load("models/classifier.pkl")
    ner_model = spacy.load("ru_core_news_lg")
```

- **Connection pooling** — для PostgreSQL и Redis используются пулы соединений.

**Пример пула соединений PostgreSQL**:
```python
import asyncpg

pool = await asyncpg.create_pool(
    host='postgres',
    port=5432,
    user='user',
    password='pass',
    database='docs',
    min_size=10,
    max_size=50
)
```

#### 3.2.5. Масштабирование базы данных и поиска

PostgreSQL является потенциальным узким местом при росте нагрузки. Применяются следующие стратегии:

- **Read replicas** — поисковые запросы направляются на реплики.
- **Партиционирование** — таблица документов разбивается по дате загрузки.

**Пример партиционирования**:
```sql
CREATE TABLE documents (
    id UUID PRIMARY KEY,
    upload_date DATE NOT NULL,
    text TEXT,
    doc_type VARCHAR(50)
) PARTITION BY RANGE (upload_date);

CREATE TABLE documents_2025_01 PARTITION OF documents
    FOR VALUES FROM ('2025-01-01') TO ('2025-02-01');
```

- **Полнотекстовый поиск** — на начальном этапе используется PostgreSQL FTS.

**Пример создания GIN-индекса**:
```sql
CREATE INDEX idx_documents_fts ON documents 
USING GIN (to_tsvector('russian', text));
```

## 4. Корректировка архитектуры системы и стека

### 4.1. Обновлённая архитектура

На основе принятых решений по валидации, предотвращению утечек и масштабированию в архитектуру добавлены следующие компоненты:

- **Очередь задач (Celery + Redis)** — обеспечивает асинхронную обработку документов, позволяет масштабировать воркеры и выдерживать пиковые нагрузки.
- **Кеш-слой (Redis)** — хранит результаты OCR, классификации, NER и поисковых запросов, снижая latency и нагрузку на тяжёлые компоненты.
- **MLflow Model Registry** — обеспечивает версионирование моделей, логирование экспериментов и воспроизводимость.
- **DVC + S3** — версионирование данных, отдельное от кода.
- **Prometheus + Grafana** — мониторинг метрик (RPS, latency, CER, длина очереди, использование GPU).

### 4.2. Обновлённая таблица технологий

| Компонент | Технология | Изменение | Обоснование |
|-----------|------------|-----------|-------------|
| Классификация | ResNet18 (fine-tuned) | Уточнён | Классическая CNN-архитектура для классификации изображений, эффективная для документов. |
| Очередь задач | Celery + Redis | Добавлен | Асинхронная обработка длительных операций, поддержка retry, масштабирование воркеров |
| Кеширование | Redis | Добавлен | In-memory хранение с TTL, поддержка сложных структур данных, репликация |
| Версионирование данных | DVC + S3 | Добавлен | Хранение больших файлов вне Git, воспроизводимость экспериментов |
| Логирование экспериментов | MLflow | Добавлен | Автоматическое логирование метрик, гиперпараметров, артефактов, версионирование моделей |
| Мониторинг | Prometheus + Grafana | Добавлен | Сбор метрик производительности и качества моделей, визуализация, алертинг |
| Поиск | PostgreSQL FTS → Elasticsearch | Уточнён | Начальный этап — PostgreSQL, при росте нагрузки — миграция на Elasticsearch |
